# Release test coverage

The admin database page offers a server-side scan plus a staging-only one-button
orchestrator. The orchestrator uses an external GitHub Actions runner so the web
request is not held open while the test runs.

## Implemented

- Existing runtime, schema, asset, template, route-guard and log diagnostics.
- Seven order payment methods, including deferred credit settlement.
- Confirmation, kitchen preparation/service, cashier cancellation.
- Rejections for paid cancellation, missing payment method, unconfirmed kitchen
  preparation, kitchen cancellation, cross-venue update and reopening closed orders.
- Room/table label and scan instruction assertions.
- Private inactive venues created inside a transaction, always rolled back;
  record absence verified. No business data is committed. Auto-increment gaps may
  remain. MySQL tables must use InnoDB before fixtures are created.
- Eight-second cooperative workflow budget, single-run file lock, existing
  endpoint throttle. Individual SQL calls can still take longer than the budget.
- Guest menu rendering intentionally does not load visit orders, order status,
  request history, or payment history. The order-submit endpoint still creates
  the guest session and order, while staff workboards remain authoritative.
- Per-case timing, aggregate SQL count/time, copy/download JSON report.
- Explicit 500/hour quota with a 350/hour planning budget and 150 reserve.
  These are planning assumptions, not measured account usage or hotel capacity.
- A staged 1, 5, 10, 20, 30, 40 and 80 busy-hotel capacity model. It separates
  cache/file activity from database-backed activity and shows the worst-case
  connection estimate if every database-backed request opens a new connection.

## One-button staging run

On a staging deployment, **Start complete release test** automatically runs the
following sequence and reports progress in the browser:

1. Verify readiness and authenticate with the staging admin account.
2. Seed disposable test batches automatically.
3. Run the server-side release scan and rollback checks.
4. Exercise guest menu browsing, ordering, service requests, staff profile login,
   Work Board rendering, and signed polling.
5. Run desktop and mobile Chromium checks for menu/category/cart interactions and
   the admin database page.
6. Run a 10-minute guest load test last: gradually ramp to 2,000 independent
   guest sessions distributed across up to 500 disposable venues, with realistic
   20–60 second think time and a browse/order/service/refresh mix. It stops early
   on 5xx/timeouts, functional failures, sustained successful-request p95 above
   3 seconds, or sustained HTTP 429s above 5%, and records per-route latency,
   errors, throttling, peak sessions, and a post-load recovery probe.
7. Verify recovery, delete all stress data, and report whether cleanup succeeded.

The 10 minutes refers only to the active guest-load window. Seeding, release
checks, browser tests, recovery, and cleanup add time to the full run. A passing
run means only that this configured guest workload completed; it does not prove
launch readiness, establish a maximum hotel count, or measure fresh database
connections directly. This short profile does not load staff Work Boards or
simulate a unique staff login per restaurant; it is not a substitute for a
separate staff-session test.

The GitHub Actions repository must contain `ZEMTAB_CALLBACK_SECRET`,
`ZEMTAB_STAGING_ADMIN_EMAIL`, `ZEMTAB_STAGING_ADMIN_PASSWORD`, and
`ZEMTAB_STAGING_BASE_URL` secrets. The
staging `.env` must contain the matching callback secret and a GitHub token with
repository-dispatch permission. If the host cannot make outbound requests to the
GitHub API, the app queues the run and the five-minute scheduled fallback picks it
up instead. The runner refuses `zemtab.com` targets and does not claim that HTTP
requests equal database connections; capacity results are measured signals for
the isolated staging database only.

## Not implemented / must not be reported as passed

- Imports/uploads, drag/resize/save/print, alert audio/background behavior, and
  slow-network throttling are outside the current browser smoke suite.
- Admin configuration, billing, destructive reset end-to-end scenarios.
- Resume after browser closure and a measured per-account hourly connection
  counter are not provided by the test runner.
- Live traffic is intentionally not generated by the admin button. A request
  unit is not a connection, especially with persistent PDO handles.

Each route's HTTP status remains NOT RUN in the report even when its controller
has an integration assertion. Full certification requires an isolated deployment
with browser automation and a separate database quota; do not drive load against
the production account's 500/hour limit.

## Local verification

`php -d extension=pdo_sqlite tests/release-workflow.php` uses only an in-memory
database, exercises the real controllers, checks all 17 results and verifies
rollback/preservation of a pre-existing venue. It does not establish MySQL hosting
compatibility or production capacity.

Also run `php tests/security-regression.php`, `node tests/product-demo.cjs`,
PHP syntax checks and Blade compilation. Those suites have their own limited
coverage; do not add their counts together and call that complete coverage.
